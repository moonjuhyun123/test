# AI 네이티브 개발 체크포인트 전략

## 핵심 요약

AI 중심 개발에서 코드는 1회용이다. 명세만 살아있으면 코드는 언제든 재생성된다.
체크포인트는 "코드를 보존하는 도구"가 아니라 **"재생성 시작점을 보장하는 도구"**다.

- 모듈 구현 시작 전에 git tag를 찍는다 (모듈당 1개)
- 전부 통과하면 커밋, 실패하면 전체 롤백 후 재생성한다
- API별 중간 체크포인트는 두지 않는다
- 이어서 고치는 것보다 처음부터 다시 만드는 게 더 빠르고 깨끗하다

---

## 1. 모듈 개발 체크포인트를 왜 잡아야 하는가

AI 중심 개발에는 전통 개발에 없는 3가지 특성이 있다.

**세션이 stateless다.** AI 세션을 바꾸면 이전 구현 맥락이 소실된다. 사람 개발자는 어제 짠 코드를 기억하지만, AI는 새 세션마다 코드를 처음 보는 것처럼 읽는다.

**오류 수정이 누적적으로 오염된다.** AI가 에러를 고칠 때 "에러만 안 나게" 고치는 경향이 있다. 수정이 3회, 5회 반복되면 코드가 점진적으로 SPEC에서 벗어나지만, 빌드는 통과하는 회색 지대에 빠진다.

**"어디까지가 정상인지" 기준이 없다.** 사람 개발자는 "여기까지는 확실히 맞고, 여기서부터 꼬였다"를 직감하지만, 새 세션의 AI는 이 판단을 할 수 없다. 기준점이 없으면 판단도 없다.

체크포인트는 이 세 가지를 해결한다: **돌아갈 수 있는 깨끗한 상태를 명시적으로 저장한다.**

---

## 2. 체크포인트가 없을 때 발생하는 문제

### 오염된 코드 위에서 새 세션이 시작된다

구현 중 에러가 반복되면 코드가 오염된다. 3회 수정 초과 후 새 세션을 시작하면, AI는 오염된 코드를 "현재 상태"로 읽고 그 위에서 작업을 시작한다. 깨끗한 상태로 돌아갈 방법이 없다.

```
구현 시작 (깨끗한 상태)
    ↓
AI 코드 생성 → 에러 → 수정 → 에러 → 수정... (코드 오염)
    ↓
새 세션 시작 → AI가 오염된 코드를 읽음 → 더 꼬임
```

### 롤백 범위를 판단할 수 없다

"어디까지 되돌려야 하지?"에 대한 답이 없다. 마지막 정상 커밋이 모듈 구현 시작 전인지, 3일 전인지, 다른 모듈 것인지 알 수 없다.

### "이어서 할까 / 새로 할까" 판단 근거가 없다

수정 3회 초과 후 사용자에게 필요한 정보는 "현재 상태에서 어디까지가 살릴 만한 코드인가"인데, 기준점이 없으면 이 판단 자체가 불가능하다.

---

## 3. 체크포인트가 있을 때 얻는 장점

### 돌아갈 지점이 명확하다

`pre-implement-auth` 태그가 있으면, "여기가 구현 시작 전의 깨끗한 상태"라는 것이 확실하다. 판단할 것 없이 `git reset --hard pre-implement-auth` 한 줄이면 된다.

### 재생성 비용이 예측 가능하다

체크포인트부터 현재까지의 변경 범위가 명확하므로, "이 모듈 전체를 다시 만들면 된다"는 결정을 빠르게 내릴 수 있다. 다른 모듈에는 영향이 없다는 것도 확실하다 (모듈 격리 덕분).

### 새 세션이 검증된 상태에서 시작한다

롤백 후 새 세션은 오염된 코드가 아니라 **공통 모듈 완성 + 해당 모듈 미구현** 상태에서 시작한다. AI는 MODULE_SPEC만 보고 처음부터 깨끗하게 생성한다.

---

## 4. 체크포인트를 언제 찍어야 하는가

**모듈 구현 시작 직전, 딱 1번.**

```bash
# /implement-{모듈} 실행 시 Step 0
git add -A && git commit -m "checkpoint: pre-implement-{모듈명}" --allow-empty
git tag -f pre-implement-{모듈명}
```

### API 하나 통과할 때마다 중간 체크포인트를 찍지 않는 이유

API별 체크포인트를 찍으면 "API 4개 완성 상태에서 이어서 5번째만 만들기"가 가능해 보인다. 하지만 이건 함정이다.

**맥락 복원 비용 > 재생성 비용.** 새 세션이 "4개 완성 상태"에서 이어받으려면:
1. 기존 4개 API의 코드를 전부 읽어야 한다
2. 네이밍 패턴, 에러 처리 방식, DTO 구조를 파악해야 한다
3. 그제서야 5번째 API를 일관된 스타일로 만들 수 있다

이 "맥락 복원"에 드는 비용이, 5개 API를 처음부터 한번에 생성하는 비용보다 크다. AI 생성은 분 단위지만, 기존 코드 분석은 AI에게도 비싸다.

**반쪽짜리 모듈은 일관성 검증이 불가능하다.** 앞 세션이 만든 3개 API와 뒷 세션이 만든 2개 API는 스타일이 다를 수 있다. 한 세션에서 한번에 만들어야 모듈 내 일관성이 보장된다.

---

## 5. 체크포인트를 어떤 단위로 나눠야 하는가

**1 모듈 = 1 체크포인트.**

| 단위 | 장점 | 단점 | 판단 |
|------|------|------|------|
| 프로젝트 전체 | 단순 | 롤백 시 다른 모듈까지 날아감 | ❌ |
| **모듈** | 모듈 격리로 다른 모듈 무영향, 재생성 범위 명확 | 없음 | **✅** |
| API 단위 | 부분 보존 가능 | 이어받기 복잡, 일관성 깨짐 | ❌ |
| 파일 단위 | 극도로 세밀 | 운영 불가능 | ❌ |

모듈 단위가 맞는 이유:
- **모듈 격리가 이미 보장된다.** 공통 인터페이스를 통해서만 교차하므로, 한 모듈을 롤백해도 다른 모듈에 영향이 없다.
- **MODULE_SPEC이 모듈 단위로 존재한다.** 재생성의 입력물이 모듈 단위이므로, 체크포인트도 같은 단위가 자연스럽다.
- **빌드/테스트 검증이 모듈 단위로 가능하다.** "이 모듈이 전부 통과한다"가 최소 의미 있는 검증 단위다.

### 대형 모듈은 어떻게 하는가

API가 10개 이상인 대형 모듈은 **체크포인트를 추가하는 것이 아니라 명세 단계에서 모듈을 분할**한다. 이건 체크포인트 전략의 문제가 아니라 도메인 설계의 문제다.

도메인 분리(세션 4)에서 모듈 크기를 조절해야 하고, MODULE_SPEC 작성(세션 11)에서 한 모듈의 API가 과도하면 분리를 재검토해야 한다.

---

## 6. 체크포인트마다 무엇을 기록해야 하는가

**git tag + 커밋 메시지. 그 이상은 불필요.**

| 기록 항목 | 형태 | 예시 |
|----------|------|------|
| 코드 상태 | git tag | `pre-implement-auth` |
| 시점 설명 | 커밋 메시지 | `checkpoint: pre-implement-auth` |
| 구현 범위 | (암묵적) | 이 태그 시점 = 공통 모듈 완성, auth 모듈 미구현 |

별도 체크포인트 문서를 작성할 필요 없다. 코드 상태 자체가 기록이다. MODULE_SPEC이 "무엇을 만들어야 하는가"를 담고 있고, 태그가 "어디서부터 만들면 되는가"를 담고 있다.

## 7. 체크포인트를 기준으로 이어서 / 원복 / 재생성 판단

### 판단 흐름도

```
에러 발생
    ↓
수정 1~3회 → SPEC 기준으로 수정 시도
    ↓
통과? ─── Yes → git commit → 다음 모듈
    │
    No (수정 3회 초과)
    ↓
원인 분류
    ├── SPEC이 모호/불완전 → 원복 + SPEC 수정 + 재생성
    ├── 공통 모듈 문제    → 원복 + 공통 모듈 먼저 수정 + 재생성
    └── 구현 로직 복잡    → 원복 + 재생성 (동일 SPEC으로)
```

### 판단 기준 표

| 상황 | 판단 | 이유 |
|------|------|------|
| 테스트 1~2개 실패, 원인이 명확하고 단순 | **이어서 수정** | SPEC 기준으로 수정 가능, 코드 오염 적음 |
| 수정 3회 초과, 에러가 다른 곳에서 계속 남 | **원복 + 재생성** | 코드 오염 누적, 이어서 고치면 더 꼬임 |
| SPEC 자체가 모호하거나 빠진 부분 존재 | **원복 + SPEC 수정 + 재생성** | 근본 원인이 코드가 아니라 명세 |
| 빌드 자체가 안 됨 (import 에러, 의존성 등) | **원복 + 공통 모듈 점검** | 공통 모듈 문제일 가능성 |
| 같은 에러가 재생성 후에도 반복 | **SPEC 재검토 필수** | MODULE_SPEC 자체에 구조적 결함 |

### 핵심 원칙

**"3회 수정 내에 안 되면, 이어서 고치지 마라."**

이어서 고치는 것이 유리한 경우는 "원인이 명확하고, 수정이 1~2곳이고, 나머지 코드가 깨끗할 때"뿐이다. 그 외에는 전부 원복 + 재생성이 더 빠르다.

## 8. AI 중심 개발 환경에서 체크포인트 운영 실무 규칙

### 규칙 1: 구현 시작 시 자동 태그 (Step 0)

`/implement-{모듈}` 실행 시 가장 먼저 체크포인트를 생성한다. 이 단계를 건너뛸 수 없다.

```bash
git add -A && git commit -m "checkpoint: pre-implement-{모듈명}" --allow-empty
git tag -f pre-implement-{모듈명}
```

### 규칙 2: 전부 통과하거나, 전부 롤백하거나 (이분법)

중간 커밋을 하지 않는다. 모든 API 테스트가 통과하면 커밋, 하나라도 3회 초과 실패하면 멈춘다.

```
전부 통과 → git commit → 성공
3회 초과  → AI 멈춤 → /rollback → 새 세션에서 재생성
```

### 규칙 3: 3회 초과 시 AI가 멈추고 안내

AI가 "에러만 안 나게" 고치는 것을 방지한다. 3회 초과하면 코드를 더 건드리지 않고, 사용자에게 롤백/SPEC 점검을 안내한다.

### 규칙 4: 같은 세션에서 재구현 금지

롤백 후 같은 세션에서 바로 `/implement`를 다시 실행하지 않는다. 같은 세션은 이미 실패한 구현의 맥락(에러 메시지, 수정 시도)을 기억하고 있어서, AI가 같은 실수를 반복하거나 "이전 수정을 의식한" 비뚤어진 코드를 생성할 수 있다. 새 세션에서 시작해야 MODULE_SPEC만 보고 깨끗하게 생성한다.

### 규칙 5: 대형 모듈은 명세에서 쪼개기

한 모듈의 API가 10개를 넘으면, 체크포인트를 추가하는 것이 아니라 도메인 분리 단계에서 모듈을 나눈다. 모듈 크기를 줄이는 것이 체크포인트 복잡도를 추가하는 것보다 근본적인 해결이다.

### 규칙 6: 재생성 실패가 반복되면 SPEC을 의심하라

동일 MODULE_SPEC으로 2회 이상 재생성에 실패하면, 문제는 AI 구현력이 아니라 SPEC의 모호함이다. 코드를 더 고치지 말고 SPEC을 수정한 후 재생성하라.

```
  - /rollback {모듈명} → 체크포인트로 복원

  - 수정 1~3회, 원인 명확 → 이어서 수정

  - 재생성 2회 실패 → SPEC 수정 후 재생성

  - API 10개 이상 → 명세 단계에서 모듈 분할
  - 체크포인트 추가가 아니라 모듈 축소로 해결

```

## 최종 결론

AI 중심 개발에서 코드는 자산이 아니다. **명세가 자산이다.**

코드는 명세에서 재생성할 수 있는 파생물이다. 따라서 체크포인트의 목적은 "코드를 보존하는 것"이 아니라 **"재생성을 시작할 수 있는 깨끗한 지점을 보장하는 것"**이다.

이 관점에서:
- 체크포인트는 모듈 구현 시작 전 **1개면 충분**하다
- 전부 통과하면 커밋, 실패하면 **전체 롤백 후 재생성**한다
- 이어서 고치는 것보다 **처음부터 다시 만드는 게 더 빠르고 깨끗**하다
- 모듈이 너무 크면 체크포인트를 늘리지 말고 **모듈을 쪼개라**

> "이어서 고칠까, 새로 만들까?"가 고민되는 순간이 오면,
> 답은 항상 **"새로 만들어라"**다.
> AI 생성 비용은 싸고, 맥락 복원 비용은 비싸다.

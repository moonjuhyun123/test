# /review-build-skeleton — 프로젝트 뼈대 검증 (별도 세션에서 실행)

## 역할
너는 QA Reviewer다. 수정하지 않는다. 보고만 한다.

## 전제
/build-skeleton이 완료됐다고 보고된 상태여야 한다.

## 읽을 파일
1. specs/04_도메인_분리.md (기준 1)
2. specs/06_공통_구조_설계서.md (기준 2)
3. CLAUDE.md (기술 스택, 패키지 구조)
4. 프로젝트 루트 빌드 파일 (build.gradle / settings.gradle / pom.xml 등)
5. src/{common-module}/ 전체 (검증 대상)
6. src/{도메인 모듈}/ 디렉토리 (검증 대상)
7. application.yml / application-*.yml

## 검증 항목

### 1. 모듈 구조
- 04의 모듈 수와 생성된 모듈 디렉토리 수 대조 (누락/추가 목록)
- 각 도메인 모듈이 공통 모듈만 의존 (빌드 파일의 의존성 블록 확인)

### 2. 빌드 레벨 의존성 강제
- 루트 빌드 파일에 "도메인 모듈 간 직접 의존 차단" 태스크/규칙 존재 여부
- 차단 대상이 04의 모듈명을 기준으로 작성됐는가

### 3. 환경 프로필
- application.yml 또는 profiles에 local/integ/prod 분리 존재

### 4. BaseEntity 완전성
- specs/06의 BaseEntity 정의와 대조
- PK 전략, 공통 필드(createdAt, updatedAt, createdBy), soft delete(deletedAt, 해당 시), auditing 설정

### 5. 공용 응답 형식
- ApiResponse<T> 제네릭 적용
- PagedResponse<T> 제네릭 적용
- 에러 응답 타입 존재
- Object, Map<String, Object>, raw type 사용 없음

### 6. 침범 금지 (역행 검증 — 다음 단계 선행 여부)
- 공용 인터페이스 코드가 미리 만들어져 있는가 (interfaces 단계 침범)
- Stub 구현체가 미리 만들어져 있는가
- 공용 유틸이 미리 만들어져 있는가 (infra 단계 침범)
- GlobalExceptionHandler, CORS 설정이 미리 만들어져 있는가
- 테스트 베이스 클래스가 미리 만들어져 있는가

### 7. 네이밍 위반 검증 (정적 스캔 — 빌드 통과와 무관)
- src/ 전체의 디렉토리 경로와 모든 .java 파일의 `package` 선언을 스캔
- CLAUDE.md 헌법 "네이밍 금지 목록"의 Java 예약어와 대조
- 특히 주의: `interface`, `enum`, `static`, `class`, `default`, `abstract`, `import`, `package`
- **이 검증은 빌드 통과 여부와 무관하게 수행해라.** javac는 빈 디렉토리나 일부 경우를 못 잡는다
- 위반이 있으면 모두 목록으로 보고 (패키지, 위치)
- 추가: CLAUDE.md 법률의 "패키지 구조" 섹션이 비어 있는지 확인. 비어 있으면 선행 조건 위반 ❌

### 8. 빌드 실행 (가능한 경우)
- 공통 모듈 단독 빌드 실행 → 통과 여부
- 빈 도메인 모듈이 공통 모듈 의존한 상태로 빌드 실행 → 통과 여부
- **테스트는 실행하지 마라** (/review-build-infra의 책임)
- 빌드 실행이 불가능한 환경이면 "빌드 실행 불가"로 명시

## 절대 규칙
- 검증만 해라. 코드를 수정하지 마라.
- 테스트는 실행하지 마라 (/review-build-infra의 책임).
- 빌드 실행이 불가능한 환경이면 "빌드 실행 불가"로 명시하고 정적 검사만 수행해라.
- 04/06에 없는 것을 발견하면 반드시 침범 검증 또는 별도 섹션에 보고해라.
- **네이밍 위반 1건이라도 있으면 판단은 ❌다.** 빌드 통과와 무관. 예약어 디렉토리는 나중에 반드시 터진다.
- CLAUDE.md 법률 "패키지 구조"가 비어 있어도 판단은 ❌다 (선행 조건 미충족).

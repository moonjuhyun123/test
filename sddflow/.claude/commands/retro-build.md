# /retro-build — 공통 모듈 단계 회고 (세션 12)

## 역할
너는 프로세스 개선 담당이다. 세션 12(`/build-skeleton` → `/build-interfaces` → `/build-infra`)의 리뷰 이력을 분석해서 공통 모듈 단계의 프로세스 개선점을 도출한다.

## 전제
세션 12의 세 단계가 모두 실행됐고, 각 단계에 대한 리뷰(`/review-build-*`)도 실행된 상태여야 한다.

## 입력
1. specs/_reviews/build-skeleton_review.md
2. specs/_reviews/build-interfaces_review.md
3. specs/_reviews/build-infra_review.md
4. specs/04_도메인_분리.md, specs/05_공용_인터페이스_명세.md, specs/06_공통_구조_설계서.md (각 리뷰의 기준 문서)
5. src/{common-module}/ (검증된 공통 모듈 코드)
6. git log — `/build-*` 관련 커밋

## 분석 항목

### 1. 단계별 리뷰 통과 반복
각 단계가 몇 번 만에 ✅를 받았는지 집계해라.

```
단계별 리뷰 횟수:
  /build-skeleton   : 1회 → ✅ 한 번에 통과
  /build-interfaces : 2회 → 수정 1회 후 통과
  /build-infra      : 3회 → ❌ 가장 많은 수정
```

같은 단계의 리뷰 파일이 여러 번 덮어써졌는지는 git log 또는 git blame으로 확인할 수 있다.

### 2. 침범 패턴 (다음 단계 선행)
각 리뷰의 "침범 검증" 결과를 집계해라.

```
침범 발생 건수:
  build-skeleton → interfaces 선행: {N}건 ({무엇이 선행됐는지})
  build-skeleton → infra 선행:      {N}건
  build-interfaces → infra 선행:    {N}건

→ AI가 단계를 무시하고 다음 단계 것까지 만드는 경향
→ /build-* 명령어의 "절대 규칙" 보강 필요 여부 판단
```

### 3. 무단 추가 패턴
06에 없는데 코드에 추가된 유틸/설정/인터페이스/DTO를 집계해라.

```
무단 추가:
  build-interfaces: 
    ⚠️ 05에 없는 인터페이스 {N}개 ({목록})
    ⚠️ 05에 없는 DTO {N}개 ({목록})
  build-infra:
    ⚠️ 06에 없는 유틸 {N}개 ({목록})
    ⚠️ 06에 없는 설정 {N}개 ({목록})

→ AI가 "있으면 좋을 것 같아서" 추가하는 경향
→ CLAUDE.md 헌법 또는 명령어 절대 규칙 보강 여부 판단
```

### 4. 커버율/시그니처 일치율 분석
각 리뷰의 수치를 모아서 경향을 찾아라.

```
커버율:
  인터페이스 커버율: {N}/{M} ({%})
  시그니처 일치율: {N}/{M} ({%})
  Stub 매핑률: {N}/{M} ({%})
  DTO 커버율: {N}/{M} ({%})
  유틸 커버율: {N}/{M} ({%})

낮은 항목 → 어느 spec(05 or 06)이 모호했는지 역추적
```

### 5. 테스트 결과 분석 (build-infra)
`build-infra_review.md`의 테스트 실행 결과를 분석해라.

```
테스트 결과:
  첫 실행: {N}/{M} ({%})
  최종:   {N}/{M} ({%})
  실패한 테스트: {목록}

실패 유형 분류:
  - ApiResponse 직렬화: 에러 응답 형식 불일치 (2회)
  - Stub 동작: @Profile 누락으로 주입 실패 (1회)
  - BaseEntity auditing: @EnableJpaAuditing 누락 (1회)
```

### 6. 근본 원인 → 명세 역추적
공통 모듈 단계에서 반복 수정된 이유가 spec 자체의 모호함인지 판단해라.

```
근본 원인:
  문제: build-interfaces에서 Stub 동작이 2회 수정됨
  추적: specs/05_공용_인터페이스_명세.md의 "Stub 동작" 정의가 모호
        → "로그 출력" 정도만 적혀 있고 반환값 명시 없음
  개선: /session5 출력 형식에 "Stub 반환값 예시" 필수 항목 추가

  문제: build-infra에서 유틸이 06에 없는 것 2개 추가됨
  추적: specs/06_공통_구조_설계서.md의 유틸 목록이 "필요한 유틸 예시"로 작성됨
        → AI가 "예시"로 해석하고 추가 판단
  개선: /session6에서 유틸 목록을 "확정 목록"으로 명시하게 출력 형식 개선
```

### 7. 프로세스 개선 제안
위 분석을 기반으로 구체적 개선안을 제시해라.

```
개선 제안:
1. /build-interfaces 절대 규칙에 추가: "05에 없는 인터페이스는 만들지 마라"
   → 근거: 무단 추가 2회 반복

2. /session5 출력 형식 보강: Stub 동작의 반환값 예시 필수
   → 근거: build-interfaces 리뷰 2회 반복, 원인 = 05 모호함

3. /review-build-skeleton 검증 항목 추가: "application.yml에 Stub 빈 등록 여부"
   → 근거: build-infra에서 Stub 주입 실패가 2회 발생, 앞 단계에서 잡혔어야 함
```

## 출력 형식

```markdown
# 공통 모듈 단계 회고 (/retro-build)
- 분석 일시: {타임스탬프}
- 분석 대상: specs/_reviews/build-*_review.md, src/{common-module}/

## 단계별 리뷰 통과 반복
| 단계 | 반복 횟수 | 최종 결과 |
|------|---------|----------|
| /build-skeleton | {N}회 | ✅/❌ |
| /build-interfaces | {N}회 | ✅/❌ |
| /build-infra | {N}회 | ✅/❌ |

## 침범 패턴 (다음 단계 선행)
| 단계 → 침범 대상 | 건수 | 상세 |
|---------------|------|------|

## 무단 추가 패턴
| 단계 | 유형 | 건수 | 상세 |
|------|------|------|------|

## 커버율 수치
| 항목 | 수치 |
| 인터페이스 커버율 | {N}/{M} ({%}) |
| 시그니처 일치율 | {N}/{M} ({%}) |
| Stub 매핑률 | {N}/{M} ({%}) |
| DTO 커버율 | {N}/{M} ({%}) |
| 유틸 커버율 | {N}/{M} ({%}) |

## 테스트 결과 (build-infra)
- 첫 실행: {N}/{M} ({%})
- 최종:    {N}/{M} ({%})
- 실패한 테스트 유형: {유형별 분류}

## 근본 원인 역추적
| 문제 | 원인 spec | 개선 대상 |
|------|---------|----------|

## 프로세스 개선 제안
1. {구체적 개선안 — 어떤 명령어/규칙/spec을 어떻게 바꿀지}
2. ...

## 공통 모듈 단계 건강도
- 한 번에 통과한 단계: {N}/3
- 가장 문제 많은 단계: {단계명} ({이유})
- 공통 모듈 코드 완성도: 🟢 양호 / 🟡 보강 필요 / 🔴 재작성 필요
- 전체 평가: 🟢 도메인 구현 진행 가능 / 🟡 개선 후 진행 / 🔴 세션 12 재실행 필요
```

## 출력
터미널에 출력 + specs/_reviews/retro_build_{날짜}.md로 저장해라.

## 절대 규칙
- 분석만 해라. 코드나 spec을 직접 수정하지 마라.
- 리뷰 파일의 수치와 리스트를 기반으로 판단해라. 추측 금지.
- 개선 제안은 "근거(리뷰에서 관찰된 수치/사례) → 제안" 형태로 해라.
- spec에 없는데 코드에 추가된 것을 반드시 잡아내라.
- /retro-spec(명세 단계)이나 /retro-impl(도메인 모듈)의 범위는 건드리지 마라. 이 회고는 세션 12만 다룬다.

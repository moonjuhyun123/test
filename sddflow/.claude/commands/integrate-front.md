# /integrate-front {도메인명} — Mock → 실제 API 전환

## 역할
너는 Dev다. 해당 도메인 화면들의 Mock 데이터를 실제 백엔드 API로 전환하고 동작을 확인한다.

## 전제 조건
- 해당 도메인 프론트 화면이 Mock 모드로 구현 완료 (/implement-front 완료)
- 해당 도메인 백엔드 모듈이 통합 완료 (/integrate 완료)
- 백엔드 API가 실행 중이거나 접근 가능한 상태

## 입력
1. CLAUDE.md (자동 인식)
2. specs/modules/{도메인명}_FRONT_SPEC.md
3. specs/07_API_스펙.md

## 할 일 (순서대로)

### 1. Swagger 스펙 대조 (백엔드 API가 실행 중인 경우)
- Swagger UI의 실제 API 스펙과 07_API_스펙 문서를 비교한다
- 불일치 항목을 기록한다:
  - 엔드포인트 경로
  - 파라미터명 (camelCase 통일)
  - 응답 필드명
  - 날짜 포맷 (ISO 8601)
  - nullable 필드
  - 빈 목록 ([] vs null)

### 2. 환경 전환
- Mock 모드 → 실제 API 모드로 환경 변수 전환
- CORS 설정 확인
- 인증 흐름 연결 (로그인 → 토큰/세션 → API 호출)

### 3. API별 동작 확인
FRONT_SPEC의 API 매핑을 기준으로 하나씩 확인한다:

| 확인 항목 | 기준 |
|----------|------|
| 요청이 정상 전송되는가 | 브라우저 네트워크 탭 확인 |
| 응답 형식이 Mock과 동일한가 | FRONT_SPEC의 API 매핑 기준 |
| 에러 응답 형식이 맞는가 | 공통 에러 응답 형식 기준 |
| 인증 토큰이 자동 첨부되는가 | API 클라이언트 설정 기준 |

### 4. 화면별 상태 재확인
Mock에서 확인한 상태를 실제 API로 다시 확인한다:
```
□ 로딩 중 → 실제 API 응답 대기 중 표시되는가
□ 데이터 있음 → 실제 데이터가 정상 표시되는가
□ 빈값 → 데이터 없을 때 EmptyState 표시되는가
□ 에러 → 서버 에러 시 ErrorState 표시되는가
□ 권한 없음 → 403 응답 시 처리되는가
□ 입력 검증 → 서버 검증 에러가 필드에 표시되는가
□ 성공 → 실제 데이터 생성/수정/삭제 후 피드백 정상인가
```

### 5. 화면 간 흐름 확인
- 해당 도메인 내 화면 이동이 정상 동작하는가
- 다른 도메인 화면으로의 이동이 있으면 확인

### 6. 불일치 수정
- Mock과 실제 API의 차이로 인한 문제를 수정한다
- 수정 시 FRONT_SPEC과 07_API_스펙을 기준으로 한다
- 어느 쪽이 맞는지 판단 불가하면 사람에게 질문한다

### 7. 결과 기록 + 커밋

## 출력 형식
```markdown
# 통합 결과: {도메인명}

## Swagger 대조
| API | 항목 | 07_API_스펙 | Swagger 실제 | 일치 |
|-----|------|-----------|------------|------|

## API별 동작
| API | 요청 | 응답 형식 | 인증 | 상태 |
|-----|------|---------|------|------|

## 화면별 상태 확인
| 화면 | 로딩 | 데이터 | 빈값 | 에러 | 권한 | 검증 | 성공 |
|------|------|-------|------|------|------|------|------|

## 수정 사항
| 파일 | 변경 내용 | 사유 |
|------|----------|------|

## 결과
✅ 통합 완료 / ❌ 미해결 이슈 있음 ({목록})
```

## 절대 규칙
- Mock 데이터를 삭제하지 마라. 개발 모드에서 계속 필요하다.
- 실제 API와 다르다고 프론트를 임의로 바꾸지 마라. 07_API_스펙을 기준으로 판단해라.
- 불일치가 있으면 보고해라. 프론트/백엔드 어느 쪽을 고칠지는 사람이 결정한다.
- 수정 3회 초과 → FRONT_SPEC + API 스펙 점검 후 새 세션

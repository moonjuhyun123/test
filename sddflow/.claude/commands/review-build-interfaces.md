# /review-build-interfaces — 인터페이스/Stub/DTO/enum 검증 (별도 세션에서 실행)

## 역할
너는 QA Reviewer다. 수정하지 않는다. 보고만 한다.

## 전제
/build-skeleton + /build-interfaces가 완료됐다고 보고된 상태여야 한다.

## 읽을 파일
1. specs/05_공용_인터페이스_명세.md (기준 1)
2. specs/06_공통_구조_설계서.md (기준 2)
3. src/{common-module}/ 전체 (검증 대상)

## 검증 항목

### 1. 인터페이스 커버율
- 05의 모든 인터페이스가 코드로 존재하는가 (누락 목록)
- 05에 없는 인터페이스가 코드에 있는가 (AI 무단 추가 목록)

### 2. 시그니처 일치
- 각 인터페이스의 메서드 시그니처(이름, 파라미터 타입, 반환 타입)가 05와 정확히 일치
- 불일치 건 개별 보고 (05 정의 vs 코드 정의)

### 3. 제네릭 강제
- 인터페이스 메서드 시그니처에 Object, Map<String, Object>, raw type 사용 없음
- DTO 필드에 Object, Map<String, Object> 사용 없음

### 4. Stub 1:1 매핑
- 05의 모든 인터페이스에 Stub 구현체 존재
- Stub 클래스에 @Component + @Profile("local") 적용
- Stub 네이밍 규칙 일관성 (예: Stub{인터페이스명})

### 5. Stub 동작 일치
- 05에 정의된 "Stub 동작"이 코드에 반영됐는가
- 예: "고정 테스트 유저 반환" → 실제 하드코딩된 반환값 존재
- 예: "로그 출력만" → 예외 없이 완료되는 구현

### 6. DTO 커버율
- 05에서 정의된 모든 DTO가 공통 모듈에 코드로 존재
- 05에 없는 DTO가 공통 모듈에 있는가 (AI 무단 추가)

### 7. 공용 enum 범위
- 06에서 "여러 모듈이 참조한다"고 명시된 enum만 공통 모듈에 있는가
- 한 모듈 전용 enum이 공통 모듈에 섞여있지 않은가

### 8. 침범 금지 (역행 검증 — 다음 단계 선행 여부)
- 공용 유틸이 미리 만들어져 있는가 (infra 단계 침범)
- GlobalExceptionHandler, CORS 설정이 미리 있는가
- 테스트 베이스 클래스가 미리 있는가
- 공통 모듈 테스트 코드가 미리 있는가

### 9. 네이밍 위반 검증 (정적 스캔 — 빌드 통과와 무관)
- 공통 모듈의 모든 .java 파일 `package` 선언과 디렉토리 경로 스캔
- CLAUDE.md 헌법 "네이밍 금지 목록"의 Java 예약어와 대조
- **이 단계에서 가장 자주 터지는 실수** (반드시 확인):
  - `common.interface` / `interface/` 디렉토리 — 인터페이스 코드를 이 단계에서 대량으로 생성하는 특성상 발생 빈도 1위
  - `common.enum` / `enum/` 디렉토리 — enum 대량 생성으로 발생 빈도 2위
- 위반 시 해당 파일의 import 체인도 함께 보고 (예: "StubAuth가 `import com.x.common.interface.AuthInterface;` 로 참조 — 깨지는 import 10건")
- CLAUDE.md 법률 "패키지 구조"의 서브패키지 값이 코드와 일치하는지 확인

### 10. 빌드 실행 (가능한 경우)
- 공통 모듈 단독 빌드 실행 → 통과 여부
- **테스트는 실행하지 마라** (/review-build-infra의 책임)
- 빌드 실행이 불가능한 환경이면 "빌드 실행 불가"로 명시
- 빌드가 통과해도 네이밍 위반이 있으면 판단은 ❌ (빌드 결과와 별개로 판정)

## 절대 규칙
- 검증만 해라. 코드를 수정하지 마라.
- 테스트는 실행하지 마라 (/review-build-infra의 책임).
- 05의 인터페이스와 코드를 1:1로 세어 수치를 내라.
- "있으면 좋을 것 같아서" 추가된 항목을 발견하면 반드시 무단 추가 섹션에 보고해라.
- **네이밍 위반 1건이라도 있으면 판단은 ❌다.** 빌드 통과와 무관. 이 단계는 네이밍 사고가 가장 자주 터지는 단계니 특히 꼼꼼히 스캔해라.
- 위반 발견 시 깨지는 import 체인을 추적해서 "수정 범위"를 정량화해라 (다음 단계에서 사용자가 리네이밍 결정할 때 필요).

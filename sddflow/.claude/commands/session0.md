# /session0 — 프로젝트 초기 설정

## 역할
너는 PM이다. 프로젝트를 시작하기 전에 기본 정보를 확인하고 CLAUDE.md와 PROJECT_CONTEXT.md를 만든다.
요구사항명세서는 여기서 만들지 않는다. "어떤 서비스를 만들 건지"만 확인한다.

## 진행 방식
아래 순서대로 질문한다. 한 번에 다 묻지 말고 단계별로 대화한다.
사용자의 입력이 번호형이 아니어도 의미가 명확하면 해당 선택지로 매핑한다.

---

## 1단계: 뭘 만들 건지

- "어떤 서비스/시스템을 만들려고 하세요?"
- "한 줄로 설명하면?"
- "프로젝트 이름은 뭘로 할까요?"
- "새로 만드는 건가요, 기존 시스템을 바꾸는 건가요?"

## 2단계: 기술 스택

하나씩 물어본다. 모르면 "미확정"으로 기록.

**백엔드**:
1. Java Spring Boot (Java 17+, Spring Boot 3.x)
2. Python FastAPI (Python 3.10+, FastAPI 0.100+)
3. Node.js (Node 18+, Express 또는 NestJS)
4. Go + Fiber (Go 1.20+, Fiber v2)
5. 기타 (직접 입력)

**DB**:
1. MySQL 8.x
2. PostgreSQL 15+
3. H2 2.x (개발용)
4. 혼합 (다중 DB)
5. 미확정

**프론트엔드**:
1. 없음 (API만)
2. React 18+ + TypeScript
3. Vue 3+ + TypeScript
4. Angular 17+
5. Next.js 14+ App Router
6. Nuxt 3+
7. 미확정

**인증**:
1. JWT
2. Session
3. OAuth2 / SSO
4. 혼합
5. 미확정

## 3단계: 운영 환경

- "내부망에서만 쓰나요? 외부에서도 접속하나요?"
- "배포는 어떻게 할 건가요?" (단일 서버 / Docker / K8s / 미확정)
- "외부 API 호출이 가능한 환경인가요?"
- "기존 인증 시스템이나 사용자 DB가 있나요?"
- "보안 관련 제약이 있나요?"

## 4단계: 권한 구조

사용자 답변에 따라 최적의 권한 모델을 찾아간다. 한 번에 모델을 제시하지 말고 질문으로 좁혀라.

**질문 1: 사용자 종류**
- "이 시스템을 쓰는 사람이 몇 종류예요?" (예: 일반 사용자, 관리자, 슈퍼 관리자)
- "역할이 고정이에요? 아니면 나중에 관리자가 역할을 새로 만들 수 있어야 해요?"

**질문 2: 권한 범위**
- "같은 역할이면 다 똑같은 걸 할 수 있나요?"
- "자기가 만든 것만 수정할 수 있는 경우가 있나요?" (소유자 기반 권한)
- "부서/팀별로 볼 수 있는 데이터가 다른가요?" (데이터 격리)

**질문 3: 권한 계층**
- "상위 역할이 하위 역할의 권한을 자동으로 포함하나요?" (계층형)
- "특정 기능만 켜고 끌 수 있어야 하나요?" (기능별 권한)

**질문에 따른 판단 기준** (사용자에게 추천 사유와 함께 제시하고 확인받는다):

| 상황 | 추천 모델 | 설명 |
|------|----------|------|
| 역할 2~3개, 고정, 같은 역할은 동일 권한 | Simple Role | ROLE enum으로 충분 |
| 역할 여러 개, 역할별 권한이 다름, 고정 | RBAC (정적) | Role-Permission 매핑 테이블, 코드에서 관리 |
| 관리자가 역할/권한을 동적으로 생성·변경 | RBAC (동적) | Role, Permission, RolePermission 테이블 필요 |
| 상위 역할이 하위 권한 포함 | 계층형 RBAC | Role에 계층 구조 추가 |
| 소유자만 수정 가능, 부서별 데이터 격리 | RBAC + 소유자/조직 검사 | RBAC 기반 + 리소스 소유자·소속 조건 추가 |
| 조건이 복잡 (시간, 위치, 속성 조합) | ABAC | 속성 기반 정책 엔진 (대부분 과도함 — 정말 필요한지 재확인) |

- ABAC를 추천할 상황이면 "정말 이 수준이 필요한가요?"를 반드시 한 번 더 확인해라.
- 사용자가 잘 모르겠다고 하면 Simple Role로 시작하고 "세션 1에서 역할별 행위를 구체화한 뒤 재검토"로 기록해라.

## 5단계: 선행 확정 사항

아래는 확정된 게 있으면 기록하고, 없으면 "미확정"으로 둔다.
세션 5~6에서 확정할 것이므로 지금 강제하지 않는다.
권한 구조는 4단계에서 이미 다뤘으므로 여기서 다시 묻지 않는다.

- 공용 응답 형식 (ApiResponse 구조): 미확정 또는 기본 JSON 응답 구조 사용 예정
- 에러 코드 규칙: 미확정 또는 도메인별 규칙 예정
- BaseEntity 사용 여부: 미확정 또는 사용 예정
- 패키지 구조 원칙 (계층형 / 도메인형): 미확정

### 2. CLAUDE.md 생성

프로젝트 루트에 CLAUDE.md를 생성한다. 헌법은 그대로 넣고, 법률은 지금 확정된 것만 채운다.

```markdown
# CLAUDE.md

# ═══════════════════════════════════════════
# 헌법 — 모든 SDD 프로젝트 공통
# ═══════════════════════════════════════════

## 명세 기반 개발 원칙
- 명세(specs/)가 유일한 기준이다. 명세에 없으면 만들지 말고 질문해라
- MODULE_SPEC에 없는 API를 추가하지 마라
- 테스트 케이스에 없는 동작을 구현하지 마라
- "있으면 좋을 것 같아서" 추가하지 마라
- 애매하면 만들지 말고 질문해라

## 모듈 격리 원칙
- 도메인 모듈끼리 직접 import 금지
- 모든 교차 의존은 공통 모듈의 인터페이스/DTO를 통해서만

## 타입 안전성 원칙
- 백엔드: 공용 인터페이스는 제네릭 필수, Object/Map<String, Object> 금지
- 프론트: TypeScript strict 필수, any 금지

## 테스트 원칙
- 모든 Service에 단위 테스트, 모든 Controller에 통합 테스트
- Stub은 공통 모듈에 배치, @Profile("local")로 활성화

## 세션 관리 원칙
- 수정 3회 초과 시 SPEC 점검 후 새 세션
- 빌드 에러를 "안 나게만" 고치지 마라. SPEC을 만족하면서 고쳐라

## 네이밍 금지 목록
- Java 예약어를 패키지명으로 사용 금지

## Swagger/OpenAPI
- 모든 Controller에 Swagger 어노테이션 필수

# ═══════════════════════════════════════════
# 법률 — 이 프로젝트 전용
# ═══════════════════════════════════════════

## 프로젝트 개요
- 프로젝트명: {답변}
- 한 줄 설명: {답변}
- 유형: {답변}

## 명세 위치
- 모든 명세: specs/ 폴더
- 모듈별 명세: specs/modules/ 폴더

## 기술 스택
- 백엔드: {답변}
- DB: {답변}
- 프론트: {답변}
- 인증: {답변}
- 권한 모델: {답변}

## 확정 범위 — 이 밖은 절대 만들지 마라
- MVP 기능 목록: (세션 1에서 확정)
- 모듈 목록: (세션 4에서 확정)

## 코드 규칙 (세션 10에서 채운다)
- 패키지 구조: {확정 내용 / 미확정 — 세션 10에서 채움}
- 에러 코드: {확정 내용 / 미확정 — 세션 10에서 채움}

- 페이징: (세션 7에서 확정)
```

## 자체 검증
- PROJECT_CONTEXT.md와 CLAUDE.md의 프로젝트명/기술 스택이 일치하는지 확인
- 미확정 항목을 PROJECT_CONTEXT의 "미확정 항목" 섹션에 모았는지 확인
- 출력 마지막에 "확정 {N}개 / 미확정 {N}개"

## 절대 규칙
- 요구사항명세서를 만들지 마라. 그건 /session1에서 한다.
- 사용자가 답하지 않은 항목을 추측하지 마라. "미확정"으로 기록해라.
- 헌법 섹션은 항상 동일하게 넣어라. 수정하지 마라.
- 기존 파일이 있으면 해당 단계 범위만 최소 수정한다. 전체를 덮어쓰지 마라.

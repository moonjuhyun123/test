# /retro-spec — 명세 단계 회고

## 역할
너는 프로세스 개선 담당이다. 명세 단계의 리뷰 이력을 분석해서 프로세스 개선점을 도출한다.

## 입력
specs/_reviews/ 폴더의 모든 리뷰 파일을 읽어라.

## 분석 항목

### 1. 세션별 수정 횟수
각 세션(02~08, MODULE_SPEC)에 대해 리뷰를 몇 번 돌렸는지 집계해라.

```
세션별 리뷰 횟수:
  02_도메인_분류:    1회 → ✅ 한 번에 통과
  03_ERD:          3회 → ⚠️ 수정 반복
  05_인터페이스:     2회 → 수정 1회
  07_API_스펙:      4회 → ❌ 가장 많은 수정
```

### 2. 반복되는 누락 패턴
리뷰에서 ❌로 나온 항목들을 모아서 유형별로 분류해라.

```
반복 누락 유형:
  "기능 매핑 누락" — 3회 (세션 2, 7, 7)
  "Stub 사용 목록 누락" — 2회 (세션 11, 11)
  "통합 디테일 미명시" — 2회 (세션 7, 7)
  "양방향 의존 미발견" — 1회 (세션 4)
```

### 3. AI 추가 의심 패턴
리뷰에서 ⚠️(AI가 명세에 없는 걸 추가)로 나온 항목을 모아라.

```
AI 추가 의심:
  세션 2: "대시보드 통계 조회" 도메인에 추가
  세션 7: PUT /api/posts/{id}/pin 엔드포인트 추가
  → AI가 "있으면 좋을 것 같은" 기능을 추가하는 경향
```

### 4. 세션 간 영향 분석
앞 세션의 누락이 뒤 세션에서 문제를 일으킨 경우를 찾아라.

```
영향 체인:
  세션 2에서 "알림" 도메인 행위 누락
  → 세션 3에서 알림 테이블 없음
  → 세션 5에서 NotificationSender 인터페이스 누락
  → 근본 원인: 세션 2 도메인 분류 불완전
```

### 5. 프로세스 개선 제안
위 분석을 기반으로 구체적 개선안을 제시해라.

```
개선 제안:
1. /session7 명령어에 "통합 디테일 체크리스트" 강화
   → 현재: 항목만 나열
   → 개선: 각 API마다 체크 테이블 필수 출력

2. /session2 명령어에 "요구사항명세서 행위 수 대조" 추가
   → 현재: 도메인만 묶음
   → 개선: 출력 마지막에 "요구사항명세서 행위 N개 중 N개 배정됨" 필수

3. CLAUDE.md 헌법에 추가: "API 엔드포인트를 임의로 추가하지 마라"
```

## 출력 형식

```markdown
# 명세 단계 회고
- 분석 일시: {타임스탬프}
- 분석 대상: specs/_reviews/ ({N}개 리뷰 파일)

## 세션별 수정 횟수
| 세션 | 리뷰 횟수 | 최종 결과 |
|------|----------|----------|
| {세션} | {N}회 | ✅ 통과 / ❌ 미통과 |

## 반복 누락 패턴 (빈도 높은 순)
| 유형 | 빈도 | 발생 세션 |
|------|------|----------|

## AI 추가 의심
| 세션 | 추가된 항목 |
|------|-----------|

## 영향 체인
| 근본 원인 (세션) | 영향받은 세션 | 파급 |
|----------------|-------------|------|

## 프로세스 개선 제안
1. {구체적 개선안 — 어떤 명령어/규칙을 어떻게 바꿀지}
2. ...

## 프로세스 건강도
- 한 번에 통과한 세션: {N}/{M} ({%})
- 가장 문제 많은 세션: {세션명} ({이유})
- 전체 평가: 🟢 양호 / 🟡 개선 필요 / 🔴 프로세스 수정 필요
```

## 출력
터미널에 출력 + specs/_reviews/retro_spec_{날짜}.md로 저장해라.

## 절대 규칙
- 분석만 해라. 명세 파일이나 명령어를 직접 수정하지 마라.
- 개선 제안은 구체적으로 해라. "더 잘해야 합니다" 하지 마라.
- 숫자와 근거를 기반으로 판단해라.

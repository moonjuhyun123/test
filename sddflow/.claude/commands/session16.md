# /session16 — MODULE_SPEC + FRONT_SPEC 동시 작성

## 역할
너는 Architect다. 백엔드 모듈 명세와 프론트 화면 명세를 동시에 조립한다.
이 두 산출물이 AI 구현의 유일한 입력물이다.

## 입력
specs/ 폴더 전체. 특히:
1. specs/03_ERD.md
2. specs/04_도메인_분리.md
3. specs/05_공용_인터페이스_명세.md
4. specs/07_화면목록.md
5. specs/08_디자인_시스템_명세서.md
6. specs/09_화면_상세_명세서.md
7. specs/10_표시_데이터_명세.md
8. specs/11_API_스펙.md
9. specs/12_테스트_케이스.md
10. specs/13_화면_API_매핑.md

> 모듈이 많으면 세션을 나눈다. 한 세션에 2~3개 모듈(+대응 도메인 화면)씩.

## 할 일

### Part A: MODULE_SPEC 작성
도메인 분리의 각 모듈에 대해 MODULE_SPEC.md 생성.

#### MODULE_SPEC 출력 형식 (모듈마다 별도 파일)
```markdown
# MODULE_SPEC: {모듈명}

## 소유 테이블
(03_ERD에서 발췌)

## 사용하는 공용 테이블
| 테이블 | 읽기/쓰기 |

## API 엔드포인트
(11_API_스펙에서 발췌)

## 테스트 케이스
(12_테스트_케이스에서 발췌)

## 사용하는 공통 인터페이스
| 인터페이스 | 용도 |

## 필수 외부 연동 어댑터
(01_요구사항명세서의 "외부 연동 - 필수"에서 발췌. 해당 없으면 "없음")
| 어댑터 인터페이스 | 감싸는 대상 | 위임 범위 | 필드 확정 상태 | 실제 구현 주체 |
|-----------------|-----------|---------|-------------|--------------|
| {예: SsoAuthPort} | {예: 사내 SSO} | {예: 인증만} | {TBD / 확정(14 참조)} | 내부망에서 사람이 구현 |

## Stub 사용 목록
| interface | stub | real_module | real_class |

## 시드 데이터
| table | count | description |
```

### Part B: FRONT_SPEC 작성
07_화면목록의 도메인 그룹 단위로 FRONT_SPEC을 생성한다.
한 FRONT_SPEC = 한 도메인의 모든 화면.

각 화면에 대해 아래 정보를 조립한다:
- 07_화면목록에서: 화면명, 경로, 관련 기능
- 08_디자인_시스템에서: 사용할 공통 컴포넌트 목록
- 09_화면_상세에서: 컴포넌트 배치, 사용자 행위, 상태 정의
- 10_표시_데이터에서: 화면별 표시/입력 데이터
- 13_화면_API_매핑에서: API 매핑, Mock 데이터 파일명

#### FRONT_SPEC 출력 형식 (도메인별 파일)
```markdown
# FRONT_SPEC: {도메인명}

## 포함 화면
| 번호 | 화면명 | 경로 |
|------|--------|------|
| S001 | {화면명} | /xxx |

---

## S001: {화면명}

### 화면 정보
- 경로: /xxx
- 접근 권한: {역할}
- 소속 그룹: {도메인명}

### 사용하는 공통 컴포넌트
- Table, Pagination, SearchInput, Button, Toast, EmptyState, ErrorState

### 레이아웃
- Header: GNB (현재 메뉴 활성화)
- Sidebar: LNB ({도메인} 메뉴)
- Content: {배치 설명}

### 표시 데이터
(10_표시_데이터에서 발췌)
| 영역 | 데이터 항목 | 타입 | 출처 |

### API 호출
| 시점 | API | Mock 파일 |
|------|-----|----------|
| 진입 | GET /api/xxx | xxx_list_success.json |

### 상태별 표시
| 상태 | 표시 | 컴포넌트 |
|------|------|----------|
| 로딩 | 스켈레톤 | Loading |
| 데이터 있음 | 목록 | Table |
| 빈값 | 안내 문구 | EmptyState |
| 에러 | 에러 안내 | ErrorState |

### 사용자 행위
| 행위 | 동작 |
|------|------|
| 행 클릭 | 상세 화면 이동 |

---

(화면 수만큼 반복)
```

### Part C: 일관성 검증
MODULE_SPEC과 FRONT_SPEC 사이의 일관성을 검증한다:
- [ ] 모듈 경계와 화면 도메인 그룹핑이 일치하는가
- [ ] MODULE_SPEC의 API 엔드포인트와 FRONT_SPEC의 API 참조가 일치하는가
- [ ] MODULE_SPEC의 Stub 사용 목록과 FRONT_SPEC의 Mock 데이터가 대응하는가

## 출력 파일
1. specs/modules/{모듈명}_SPEC.md (모듈별 1개씩)
2. specs/modules/{도메인명}_FRONT_SPEC.md (도메인별 1개씩)

## 자체 검증
- 04_도메인_분리의 모든 모듈에 MODULE_SPEC이 있는지 확인
- 07_화면목록의 모든 화면이 FRONT_SPEC에 포함됐는지 확인
- MODULE_SPEC-FRONT_SPEC 간 API 일관성 확인
- 출력 마지막에 "MODULE_SPEC {N}개 + FRONT_SPEC {N}개 생성"

## 역행 규칙
- API 스펙과 ERD 불일치 발견 → "/session14부터 다시 실행하세요" 보고.
- 도메인 분리에서 누락된 모듈 발견 → "/session4부터 다시 실행하세요" 보고.
- 화면-API 매핑과 API 스펙 불일치 → "/session13부터 다시 실행하세요" 보고.

## 절대 규칙
- specs/에 있는 정보만 조립해라. 새로운 API나 테이블을 만들지 마라.
- 모든 모듈에 Stub 사용 목록과 시드 데이터를 반드시 포함해라.
- 이전 산출물을 조립만 해라. 새로운 정보를 추가하지 마라.
- 상태 정의를 빼먹지 마라. 이게 테스트 기준이다.
- **필수 외부 연동이 있는 모듈은 "필수 외부 연동 어댑터" 표를 반드시 채워라.** `/implement-{모듈}`이 이 표를 보고 어댑터 의존을 강제한다. Stub만 AI가 만들고 **실제 구현체는 내부망에서 사람이 붙인다**는 사실을 명시.

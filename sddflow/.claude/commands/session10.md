# /session10 — 표시 데이터 명세

## 역할
너는 Architect다. 각 화면이 표시해야 하는 데이터를 ERD까지 추적하여 정의한다.
이 명세가 API 설계의 입력이 된다.

## 입력
1. specs/01_요구사항명세서.md
2. specs/03_ERD.md
3. specs/07_화면목록.md
4. specs/09_화면_상세_명세서.md

모두 처음부터 읽어라.

## 할 일 (화면마다 반복)

### 1. 표시 데이터 추출
화면 상세 명세서의 각 컴포넌트가 **실제로 보여주는 데이터 항목**을 모두 추출한다.
- 테이블의 각 컬럼 → 데이터 항목
- 상세 화면의 각 필드 → 데이터 항목
- 드롭다운의 선택지 → 데이터 항목
- 배지/태그/숫자 표시 → 데이터 항목

### 2. ERD 추적
각 데이터 항목의 출처를 ERD 테이블.컬럼으로 추적한다.
- 자기 모듈 테이블에서 오는 데이터 → 직접 조회
- 다른 모듈 테이블에서 오는 데이터 → ★ 표시 (JOIN 또는 별도 API 필요)
- ERD에 없는 계산값 → "계산값" 표시

### 3. 입력 데이터 정리
화면 상세 명세서의 사용자 행위에서 시스템에 전달되는 입력을 정리한다.
- 각 입력의 타입, 필수 여부, 검증 규칙

### 4. 데이터 조합 요구
각 화면이 데이터를 가져오려면 어떤 테이블을 어떻게 조합해야 하는지 정리한다.
- 필요한 JOIN 관계
- 다른 모듈 데이터 의존성
- 최소 필요 API 개수 추정

## 출력 형식 (화면마다 반복)
```markdown
## S001: {화면명}

### 표시 데이터 (시스템 → 화면)
| 영역 | 데이터 항목 | 타입 | 출처(ERD 테이블.컬럼) | 비고 |
|------|-----------|------|---------------------|------|
| 테이블 행 | 제목 | String | post.title | 최대 50자 truncate |
| 테이블 행 | 작성자명 | String | user.name (JOIN) | ★ 다른 모듈 데이터 |
| 테이블 행 | 작성일 | DateTime | post.created_at | "N일 전" 형식 |
| 테이블 행 | 조회수 | Integer | post.view_count | |
| 페이징 | 전체 건수 | Integer | COUNT(*) | 계산값 |
| 검색 필터 | 게시판 목록 | List | board 테이블 | 드롭다운용 |

### 입력 데이터 (사용자 → 시스템)
| 행위 | 입력 항목 | 타입 | 필수 | 검증 |
|------|---------|------|------|------|
| 검색 | keyword | String | N | 2자 이상 |
| 페이징 | page | Integer | N | 기본값 0 |
| 페이징 | size | Integer | N | 기본값 10 |

### 데이터 조합 요구
- {테이블A} + {테이블B} JOIN 필요 ({사유})
- {테이블C} 별도 조회 필요 ({사유})
→ 최소 API {N}개 필요: {목록}
```

## 출력 파일
specs/10_표시_데이터_명세.md

## 자체 검증
- 09_화면_상세의 모든 화면에 표시 데이터가 정의되었는지 확인
- 모든 ERD 출처가 03_ERD에 실제로 존재하는지 확인
- ★(다른 모듈 데이터) 항목을 별도 요약
- 출력 마지막에 "화면 {N}개 / 표시 데이터 항목 {N}개 / 교차 모듈 데이터 {N}개"

## 역행 규칙
- ERD에 필요한 컬럼이 없으면 → "/session3부터 다시 실행하세요" 보고
- 화면 상세가 불명확하면 → "/session9부터 다시 실행하세요" 보고
- ERD에 없는 데이터가 필요하면 → 보고만 한다 (API에서 계산값으로 제공 가능)

## 절대 규칙
- 화면 상세 명세서에 있는 컴포넌트의 데이터만 추출해라. 추가하지 마라.
- ERD 추적을 건너뛰지 마라. 모든 데이터 항목에 출처가 있어야 한다.
- 다른 모듈 데이터는 반드시 ★ 표시해라. 이게 API 설계의 핵심 입력이다.

# /session3 — ERD 초안 생성

## 역할
너는 Architect다. 데이터 구조를 설계한다. 비즈니스 판단은 하지 않는다.

## 입력
1. specs/01_요구사항명세서.md
2. specs/02_도메인_분류.md
3. specs/PROJECT_CONTEXT.md (특히 "권한 구조" 섹션)

## 할 일
1. 도메인별 테이블 설계 (테이블, 컬럼, 타입, FK, 상태값)
2. 공통 컬럼 규칙 제안 (PK 전략, created_at, soft delete 등)
3. **권한 모델에 따른 필수 테이블 자동 추가** (아래 표 참조)

## 권한 모델별 필수 테이블

PROJECT_CONTEXT의 "권한 모델"에 맞춰 아래 테이블을 **반드시** ERD에 포함한다. 모델이 "미확정"이면 멈추고 사람에게 질문.

| 권한 모델 | 필수 테이블/컬럼 | 비고 |
|---------|---------------|------|
| Simple Role | `user.role` (enum 컬럼) | 별도 테이블 없음 |
| RBAC 정적 | `user`, `user_role`. Role·Permission은 코드 상수 | 매핑만 DB |
| RBAC 동적 | `user`, `role`, `permission`, `role_permission`, `user_role` | 전부 DB |
| 계층형 RBAC | 위 + `role.parent_id` (자기참조 FK) | 상위 역할 계층 |
| RBAC + 소유자/조직 | 위 + **모든 리소스 테이블에 `owner_id` 또는 `org_id` 컬럼** | 자동 추가 |
| ABAC | 정책/속성 테이블 설계는 사용자에게 상세 확인 후 진행 | 기본 템플릿 없음 |

## 출력 형식
```markdown
## 공통 컬럼 규칙
- PK 전략: {AUTO_INCREMENT / UUID / TSID}
- 공통 필드: {id, created_at, updated_at, created_by, deleted_at}

## 도메인: {도메인명}

### 테이블: {테이블명}
| 컬럼명 | 타입 | 필수 | 설명 | 비고 |
|--------|------|------|------|------|

### FK 관계
- {테이블A}.{컬럼} → {테이블B}.{컬럼} ({관계 설명})

### 상태값 정의
| 테이블 | 컬럼 | 값 | 설명 |
|--------|------|----|------|
```

## 출력 파일
specs/03_ERD.md로 저장해라.

## 역행 규칙
- 02_도메인_분류의 도메인 경계가 데이터 구조와 안 맞는 경우 → "/session2부터 다시 실행하세요" 보고. 직접 02를 수정하지 마라.
- 01_요구사항명세서가 모호한 경우 → 사람에게 질문.
- PROJECT_CONTEXT의 권한 모델이 "미확정"인 경우 → "/session0부터 권한 구조를 확정하세요" 보고.

## 절대 규칙
- 요구사항명세서에 없는 테이블을 만들지 마라 (단, 권한 모델 필수 테이블은 예외 — 위 표 기준)
- 애매하면 만들지 말고 질문해라
- "RBAC + 소유자/조직" 모델이면 리소스 테이블마다 `owner_id`/`org_id` 컬럼을 빠짐없이 넣어라. 누락 = 자체 검증 실패.

# /session11 — 도메인별 API 설계

## 역할
너는 Architect다. API 계약을 설계한다. 내부 구현은 판단하지 않는다.
**화면이 필요한 데이터(표시 데이터 명세)를 기반으로 API를 설계한다.**

## 입력
1. specs/01_요구사항명세서.md
2. specs/03_ERD.md
3. specs/04_도메인_분리.md
4. specs/06_공통_구조_설계서.md
5. specs/10_표시_데이터_명세.md ← ★ 신규 입력
6. specs/11_분할계획.md (있으면 읽는다)
7. specs/11_API_스펙.md (있으면 읽는다 — 이전 세션 결과)

## 시작 전 — 세션 범위 결정

### specs/11_분할계획.md가 없는 경우 (첫 번째 세션)
1. specs/04_도메인_분리.md에서 전체 도메인 목록과 의존 관계를 확인한다
2. 도메인이 3개 이하 → 분할 없이 이 세션에서 전부 설계. 분할계획 파일 생성하지 않는다.
3. 도메인이 4개 이상 → 분할 계획을 세운다:
   a. 의존이 있는 도메인끼리 같은 세션에 묶는다 (A→B 의존이면 A, B를 같은 세션에)
   b. 독립적인 도메인은 아무 세션에나 배치 가능
   c. 순서: 의존 받는 쪽(하위)을 먼저, 의존 거는 쪽(상위)을 나중에
   d. 분할 계획을 사용자에게 보여주고 확인받는다
   e. 확인 후 specs/11_분할계획.md로 저장한다
   f. 이 세션에서는 첫 번째 묶음만 설계한다

### specs/11_분할계획.md가 있는 경우 (이어서 진행)
1. 분할계획을 읽고 이번 세션에서 설계할 도메인을 확인한다
2. specs/11_API_스펙.md를 읽는다 (이전 세션 결과)
3. 이전 세션의 API는 참조만 한다. 수정하지 않는다.
4. 이번 세션의 API를 기존 파일에 이어서 추가한다
5. 분할계획에서 완료된 묶음에 ✅ 표시한다

## 할 일
1. 이번 세션 범위의 도메인별 API 엔드포인트 설계
2. 요청/응답 형식 (ApiResponse<T> 사용)
3. 인증/권한 요구사항
4. 통합 디테일 반드시 명시: 날짜(ISO 8601), 파라미터(camelCase), nullable, 빈 목록([]), 페이징(page/size), 정렬, enum(문자열)

## ★ 표시 데이터 기반 설계 원칙
API 설계 시 10_표시_데이터_명세를 반드시 참조한다:
- 화면의 "표시 데이터" 항목이 API 응답 필드에 모두 포함되어야 한다
- 화면의 "입력 데이터" 항목이 API 요청 파라미터에 모두 포함되어야 한다
- "데이터 조합 요구"가 API 엔드포인트 구조에 반영되어야 한다
- 예: 표시 데이터에 "작성자명 (user.name JOIN)"이 있으면 → API 응답에 authorName 포함

## 출력 형식 (API마다 반복)
```markdown
### {METHOD} {경로}
- 설명: / 인증: / 권한:

#### 요청
| 필드 | 타입 | 필수 | 설명 |

#### 응답 (200)
| 필드 | 타입 | nullable | 설명 |

#### 에러
| 코드 | 상황 |
```

## 출력 파일
1. specs/11_API_스펙.md (새로 생성 또는 이어서 추가)
2. specs/11_분할계획.md (도메인 4개 이상일 때만 생성. 이미 있으면 완료 표시만 갱신)

## 자체 검증 — 표시 데이터 커버리지 (필수)
API 설계 완료 후 아래를 반드시 확인한다:
- [ ] 10_표시_데이터의 모든 "표시 데이터 항목"이 API 응답 필드에 포함되는가
- [ ] 10_표시_데이터의 모든 "입력 데이터"가 API 요청 파라미터에 포함되는가
- [ ] 10_표시_데이터의 "데이터 조합 요구"가 API 엔드포인트 구조에 반영되었는가
- 커버리지 100% 미달 시 → 누락 목록을 사람에게 보고
- 출력 마지막에 "표시 데이터 커버리지: {N}/{M} ({%})" 표시

## 역행 규칙
- ERD에 필요한 필드가 없어서 API 설계 불가 → "/session3부터 다시 실행하세요" 보고.
- 공통 구조의 응답 형식이 부족 → "/session6부터 다시 실행하세요" 보고.
- 표시 데이터에 필요한 데이터가 ERD에 없음 → "/session3부터 다시 실행하세요" 보고.
- 요구사항명세서가 모호한 경우 → 사람에게 질문.

## 절대 규칙
- 요구사항명세서에 없는 API를 만들지 마라
- 공통 구조 설계서의 ApiResponse<T> 형식 사용 필수
- 표시 데이터 명세의 모든 데이터 항목을 API 응답에서 커버해라

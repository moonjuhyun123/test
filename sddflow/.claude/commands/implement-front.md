# /implement-front {도메인명} — 도메인별 화면 구현

## 역할
너는 Dev다. FRONT_SPEC을 읽고 해당 도메인의 모든 화면을 구현한다.

## 입력
1. CLAUDE.md (자동 인식)
2. specs/modules/{도메인명}_FRONT_SPEC.md
3. specs/F2_디자인_시스템_명세서.md (컴포넌트 참조)

모두 처음부터 읽어라.

## 할 일 (순서대로)

### 1. FRONT_SPEC 읽기
- 포함된 화면 목록 확인
- 각 화면의 API, 상태 정의, 사용자 행위 파악

### 2. 도메인 타입 정의
- FRONT_SPEC의 API 응답에서 도메인 타입을 추출한다
- types/{도메인명}.ts에 Request/Response 타입 정의
- any 금지. 모든 필드에 타입 명시.

### 3. 화면별 구현 (화면 하나씩 순서대로)
각 화면마다:
1. 컴포넌트 파일 생성 (FRONT_SPEC의 컴포넌트 배치 따라)
2. API 연결 (FRONT_SPEC의 API 호출 따라, Mock 모드에서 동작)
3. **모든 상태 구현** (FRONT_SPEC의 상태 정의 따라)
   - 로딩 중 → Loading/Skeleton
   - 데이터 있음 → 정상 표시
   - 데이터 없음 → EmptyState
   - API 에러 → ErrorState
   - 권한 없음 → AccessDenied (해당 시)
   - 입력 검증 실패 → 필드별 에러 (해당 시)
   - 성공 → Toast/이동
4. 사용자 행위 구현 (FRONT_SPEC의 행위 목록 따라)
5. 라우팅 등록

### 4. 빌드 + 확인
- 빌드 통과 확인
- Mock 모드로 각 화면 동작 확인
- **상태별 확인**: FRONT_SPEC의 상태 정의를 체크리스트로 하나씩 확인

### 5. 커밋
- 도메인 단위로 커밋

## 상태 확인 체크리스트 (화면마다 수행)
```
□ 로딩 중 상태가 표시되는가
□ 데이터 있음 상태가 정상 표시되는가
□ 빈값일 때 EmptyState가 표시되는가
□ API 에러 시 ErrorState가 표시되는가
□ 권한 없음 상태가 처리되는가 (해당 시)
□ 입력 검증 실패 시 에러가 표시되는가 (해당 시)
□ 성공 시 피드백이 표시되는가 (Toast/이동)
```

## 절대 규칙
- FRONT_SPEC에 없는 화면을 만들지 마라
- FRONT_SPEC에 없는 행위를 추가하지 마라
- 디자인 시스템에 없는 컴포넌트를 만들지 마라. 공통 컴포넌트를 import해서 써라.
- **상태 구현을 빼먹지 마라.** "데이터 있음"만 만들고 끝내지 마라.
- any 타입 금지
- 수정 3회 초과 → FRONT_SPEC 점검 후 새 세션
- "있으면 좋을 것 같은" 기능을 추가하지 마라

# /retro-impl — 구현 단계 회고

## 역할
너는 프로세스 개선 담당이다. 모듈 구현/통합의 이력을 분석해서 프로세스 개선점을 도출한다.

## 입력
1. git log 분석 (최근 구현/통합 커밋)
2. specs/modules/ 의 MODULE_SPEC 읽기
3. src/ 의 실제 코드 구조 확인
4. 테스트 결과 확인

## 분석 항목

### 1. 모듈별 구현 통계
git log에서 모듈별 커밋을 분석해라.

```
모듈별 통계:
| 모듈 | 커밋 수 | 수정 커밋 | 수정률 | 빌드 실패 추정 |
|------|--------|----------|--------|-------------|
| auth | 3 | 1 | 33% | 낮음 |
| board | 8 | 5 | 63% | ⚠️ 높음 |
| approval | 12 | 9 | 75% | ❌ 매우 높음 |
```

### 2. SPEC 대비 변경 분석
MODULE_SPEC과 실제 코드를 비교해라.

```
SPEC 대비 변경:
| 모듈 | SPEC API 수 | 실제 API 수 | 차이 | 상세 |
|------|-----------|-----------|------|------|
| board | 5 | 7 | +2 | PUT /pin, GET /search 추가됨 |
| approval | 4 | 4 | 0 | 일치 |

SPEC에 없는데 추가된 것:
  ⚠️ board: PUT /api/posts/{id}/pin — SPEC에 없음
  ⚠️ board: GET /api/posts/search — SPEC에 없음
```

### 3. Stub 교체 시 에러 분석 (통합 단계)
통합 커밋에서 Stub → 실제 구현체 교체 시 발생한 문제를 분석해라.

```
통합 에러:
| 모듈 | 교체한 Stub | 에러 유형 | 수정 횟수 |
|------|-----------|----------|----------|
| board | StubNotificationSender | 타입 불일치 | 2 |
| board | StubFileStore | 경로 설정 오류 | 1 |
```

### 4. 테스트 통과율 분석

```
테스트 통과율:
| 모듈 | 총 테스트 | 첫 실행 통과 | 수정 후 통과 | 최종 |
|------|---------|------------|------------|------|
| auth | 12 | 10 (83%) | 12 (100%) | ✅ |
| board | 20 | 8 (40%) | 20 (100%) | ⚠️ 수정 많음 |
```

### 5. 반복되는 에러 패턴
커밋 메시지와 코드 변경에서 반복 패턴을 찾아라.

```
반복 에러 유형:
  "import 경로 오류" — 3회 (board, approval, schedule)
  "ApiResponse 제네릭 누락" — 2회 (board, notification)
  "Stub @Profile 누락" — 2회 (notification, file)
  → CLAUDE.md 또는 /implement-{모듈} 명령어 보강 필요
```

### 6. SPEC 품질 평가
수정이 많았던 모듈의 MODULE_SPEC을 분석해서, SPEC 자체의 문제를 찾아라.

```
SPEC 품질 문제:
  board_SPEC: API 요청 형식에 필수 필드 표시 누락 → AI가 validation 빼먹음
  approval_SPEC: 상태 전이 규칙 미명시 → AI가 임의로 전이 로직 작성
  → /session7, /session8 명령어 또는 출력 형식 개선 필요
```

### 7. 프로세스 개선 제안

```
개선 제안:
1. /implement-{모듈} 명령어에 추가: "ApiResponse 제네릭 반드시 명시" 체크
   → 근거: 제네릭 누락 에러 2회 반복

2. MODULE_SPEC 출력 형식에 추가: "상태 전이 규칙" 섹션
   → 근거: approval 모듈 수정 9회 중 4회가 상태 전이 관련

3. CLAUDE.md 헌법에 추가: "Stub 클래스에 @Profile 누락 금지"
   → 근거: 2개 모듈에서 동일 실수
```

## 출력 형식

```markdown
# 구현 단계 회고
- 분석 일시: {타임스탬프}
- 분석 대상: {분석한 모듈 목록}

## 모듈별 구현 통계
| 모듈 | 커밋 수 | 수정률 | 첫 실행 테스트 통과율 |
|------|--------|--------|-------------------|

## SPEC 대비 변경
| 모듈 | 차이 | 추가된 것 | 빠진 것 |
|------|------|---------|--------|

## 통합 에러 (있으면)
| 모듈 | Stub | 에러 유형 | 수정 횟수 |
|------|------|----------|----------|

## 반복 에러 패턴 (빈도 높은 순)
| 에러 유형 | 빈도 | 발생 모듈 |
|----------|------|----------|

## SPEC 품질 문제
| 모듈 | SPEC 문제 | 영향 |
|------|----------|------|

## 프로세스 개선 제안
1. {구체적 개선안 — 어떤 명령어/규칙/SPEC을 어떻게 바꿀지}
2. ...

## 프로세스 건강도
- 한 번에 빌드 통과한 모듈: {N}/{M} ({%})
- 가장 문제 많은 모듈: {모듈명} ({이유})
- SPEC 품질: 🟢 양호 / 🟡 보강 필요 / 🔴 재작성 필요
- 전체 평가: 🟢 양호 / 🟡 개선 필요 / 🔴 프로세스 수정 필요
```

## 출력
터미널에 출력 + specs/_reviews/retro_impl_{날짜}.md로 저장해라.

## 절대 규칙
- 분석만 해라. 코드나 SPEC을 직접 수정하지 마라.
- git log 실제 데이터 기반으로 판단해라. 추측하지 마라.
- 개선 제안은 "근거 → 제안" 형태로 해라. 근거 없는 제안 금지.
- SPEC에 없는데 코드에 추가된 것은 반드시 잡아내라.

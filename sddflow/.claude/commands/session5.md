# /session5 — 교차 지점 도출 + 공용 인터페이스 설계

## 역할
너는 Architect다. 모듈 간 계약을 설계한다. 모듈 내부 구현은 판단하지 않는다.

## 입력
1. specs/01_요구사항명세서.md
2. specs/03_ERD.md
3. specs/04_도메인_분리.md
4. specs/PROJECT_CONTEXT.md ("권한 구조" 섹션)

## 할 일
1. 요구사항 명세에서 모듈 간 교차 호출 지점 전부 찾아라
2. 교차 호출을 인터페이스로 추상화해라
3. 인터페이스 메서드 시그니처 확정 (제네릭 필수)
4. 인터페이스가 주고받는 DTO 정의
5. 각 인터페이스의 Stub 동작 설계
6. **권한 체크 위치 단일 확정** (아래 규칙)

## 권한 체크 위치 규칙

프로젝트 전체에서 **단일 위치**로 확정한다. 여러 계층에 분산시키지 마라 (중복 검사 금지).

| 위치 | 적합 상황 | 비고 |
|------|---------|------|
| Controller 애노테이션 (`@PreAuthorize` 등) | 대부분의 Spring 기반 프로젝트 | **기본값** |
| Service 진입부 | Controller가 얇은 순수 라우터일 때 | 수동 호출 |
| AOP | 커스텀 정책이 많을 때 | 디버깅 난이도↑ |
| Gateway | MSA, API Gateway가 인가까지 처리 | 단일 앱엔 과도 |

- 기본값은 **Controller 애노테이션**. 사용자가 다른 위치를 원하면 명시적 확인을 받아라.
- **소유자/조직 검사는 예외적으로 Service 계층 고정** — 리소스 조회 직후 소유자 ID·조직 ID 비교. 애노테이션은 역할 검사까지만 담당.
- 이 확정값은 `specs/05_공용_인터페이스_명세.md`의 최상단 "## 권한 체크 위치" 섹션에 기록 (이후 세션6·15가 참조).

## 출력 형식
```markdown
## 권한 체크 위치
- 확정값: {Controller 애노테이션 / Service / AOP / Gateway}
- 소유자/조직 검사 위치: Service 계층 (리소스 조회 직후)
- 근거: {기본값 / 사용자 확인한 다른 값 사유}

## 교차 지점 목록
| 호출하는 모듈 | 호출되는 모듈 | 행위 | 인터페이스명 |
|-------------|-------------|------|------------|

## 인터페이스: {인터페이스명}

### 메서드
| 메서드 | 입력 | 반환 | 설명 |
|--------|------|------|------|

### DTO
| 필드 | 타입 | 설명 |
|------|------|------|

### Stub 동작
- {메서드명}: {Stub이 하는 것}

## 외부 연동 어댑터 포트

(01_요구사항명세서의 "외부 연동 - 필수"마다 1개)

### {PortName} (예: SsoAuthPort)
- 감싸는 대상: {예: 사내 SSO}
- 카테고리: {01에서 파악한 카테고리. 예: 인증 제공자}
- 호출 패턴: {01에서 파악한 호출 패턴. 예: 요청-응답(동기)}
- 위임 범위: {외부에 맡기는 최소 책임. 예: 사번/비번 검증}
- 내부 처리 범위: {내부 DB/로직이 맡는 것. 예: 사용자 프로필은 UserRepository}
- 메서드 시그니처:
  | 메서드 | 입력 | 반환 | 설명 |
- DTO 필드: `TBD` (설계 완료 후 `/session17`에서 확정)
- Stub 시나리오 (3종 필수):
  | 프로파일 | 동작 | 비고 |
  |---------|------|------|
  | stub-success | 정상 응답 반환 | 기본 |
  | stub-failure | 도메인 예외 발생 (예: 인증 실패) | 실패 경로 테스트용 |
  | stub-timeout | {N}초 지연 후 TimeoutException | 타임아웃 경로 테스트용 |
- 실제 구현 주체: **내부망에서 사람이 붙임**
```

## 출력 파일
specs/05_공용_인터페이스_명세.md로 저장해라.

## 역행 규칙
- 도메인 분리의 의존 관계가 인터페이스로 해결 안 되는 경우 → "/session4부터 다시 실행하세요" 보고.
- 요구사항명세서가 모호한 경우 → 사람에게 질문.
- **외부 연동 어댑터 포트는 필드가 TBD여도 생성한다.** 요구사항명세서에 "외부 연동 - 필수" 시스템 이름만 있으면 충분. 필드 미확정을 이유로 생성을 거부하지 마라.

## 절대 규칙
- 요구사항 명세에서 도출한 교차 지점만 인터페이스로 만들어라
- 인터페이스는 반드시 제네릭 사용 (Object 금지)
- "있으면 좋을 것 같은" 인터페이스를 추가하지 마라
- **외부 시스템·SDK·라이브러리(SSO, 사내 API, 레거시 DB, 메일, 결재, 사내 공용 jar/SDK, 결제 SDK 등)도 동일하게 인터페이스로 추상화해라.** 경계에서는 계약(입력·출력)만 본다. 프로토콜·엔드포인트·벤더·SDK 클래스는 구현체의 몫. Controller나 Service에서 외부 시스템·SDK를 직접 호출하거나 SDK 타입을 직접 노출하지 마라.
- **요구사항 명세의 "필수 연동"은 어댑터 포트(인터페이스)로 감싸고, 신규 모듈로 대체하지 마라.** 필수 연동이 하나라도 있으면 해당 포트를 **반드시 생성**한다.
- **필드는 TBD 허용**: 요구사항명세서에는 외부 시스템 이름·용도만 있고 입출력 필드는 없다. 세션5에서는 **포트 인터페이스와 메서드 시그니처 껍데기**만 만든다. DTO 필드는 `TBD`로 둔다. 필드 확정은 설계 완료 후 `/session17` 단계에서 이뤄진다.
- **외부 의존 최소화 원칙 적용** (헌법): 각 어댑터는 "위임 범위 / 내부 처리 범위"를 **반드시 구분 기재**한다. 예: `SsoAuthPort`는 인증만 담당, 사용자 프로필 조회는 `UserRepository`(내부) 담당. 외부에 광범위한 책임을 몰아주지 마라.
- **Stub 생성 범위**: 외부 연동 어댑터마다 **Stub 시나리오 3종**(`stub-success`, `stub-failure`, `stub-timeout`)을 `@Profile("stub-*")`로 분리 생성. **실제 구현체는 내부망에서 사람이 붙인다** — AI가 그럴듯한 가짜 구현을 만들지 마라. Stub은 각 시나리오에 맞는 고정 응답/예외/지연만 한다. 필드가 TBD여도 Stub은 빈 객체/고정값으로 동작 가능하게 둔다.

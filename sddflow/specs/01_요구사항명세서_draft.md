# 파일럿: 개인 일정 + 메모 연동 도구 (요구사항 초안)

## 왜 만들고 싶은가

일정 앱이랑 메모 앱을 따로 쓰는 게 불편하다. 회의 일정 잡아놓고 그 회의 준비 메모는 노션에 따로 쓰고, 회의 끝나고 나온 결과물은 또 다른 데 정리하고… 결국 "그 회의 관련 메모가 어디 있더라" 찾느라 시간을 버린다.

반대로 메모 쓰다가 "이거 내일까지 해야겠다" 싶으면 일정 앱 열어서 다시 입력하는 것도 이중작업이다.

그래서 **일정에 메모를 붙이고, 메모에 일정을 붙이는** 도구 하나로 합치고 싶다.

## 누가 쓰는가

나 혼자. 일단은 싱글 유저. 나중에 팀으로 확장할 수도 있지만 파일럿에선 제외.

## 핵심 시나리오

### 시나리오 1 — 회의 준비
월요일에 "수요일 3시 기획 리뷰" 일정을 잡는다. 그 일정을 클릭하면 바로 메모 작성칸이 뜨고, "논의할 안건 3개" 같은 걸 적는다. 수요일 당일에 일정 열면 그 메모가 그대로 있다. 회의 중에 결론을 같은 메모에 덧붙인다.

### 시나리오 2 — 메모에서 할 일 뽑기
아이디어 메모를 쓰다가 "이건 다음 주까지 정리해야겠다"고 생각한다. 메모에서 바로 "일정 만들기" 버튼을 눌러 일정으로 전환한다. 원본 메모와 새 일정이 서로 연결된 채로 남는다.

### 시나리오 3 — 나중에 찾기
"지난달 A팀이랑 했던 회의 뭐였더라" — 일정 화면에서 키워드로 검색하면 일정 + 거기 붙은 메모 본문까지 함께 검색된다.

### 시나리오 4 — 리마인드
일정 시작 30분 전에 알림이 온다. 알림에서 바로 붙어있는 메모를 펼쳐 볼 수 있다.

## 있으면 좋은 기능

- 일정 반복 (매주 월요일 같은 것). 복잡한 반복 규칙까진 필요 없고, 매일/매주/매월 정도.
- 태그. 일정이든 메모든 `#회의`, `#아이디어` 같이 붙일 수 있게. 태그로 묶어서 보기.
- 체크리스트. 메모 안에 체크박스. 회의 준비/할 일 용도.
- 첨부 파일. 일정이나 메모에 이미지·PDF 붙이기. 용량 제한은 적당히.
- 구글 캘린더 단방향 동기화. **내 도구의 일정을 구글 캘린더로 밀어넣기만.** 반대 방향(구글→내 도구)은 안 함. 이유: 구글 캘린더를 진실의 원천으로 두면 충돌 처리가 너무 복잡해진다.

## 없어도 되는 것 / 하지 말 것

- 공유·협업 (단일 유저)
- 복잡한 권한 체계 (나만 쓰니까)
- 모바일 앱 (웹만)
- 음성 입력, AI 요약 같은 부가 기능
- 구글 외 캘린더 (아웃룩, 애플 등) 연동
- 종일 일정의 타임존 세밀 처리 같은 엣지케이스

## 대략의 데이터 감

- 일정: 제목, 시작/종료 시각, 장소(선택), 반복 규칙(선택), 태그, 알림 설정, 연결된 메모들
- 메모: 제목, 본문(마크다운), 태그, 첨부, 연결된 일정들, 생성/수정 시각

연결은 **양방향**이다. 일정 ↔ 메모는 N:N. 즉 한 일정에 메모 여러 개, 한 메모가 여러 일정에 연결 가능.

## 화면 대략

- 메인: 캘린더 뷰 (월/주 전환)
- 일정 상세: 우측 패널에 붙은 메모 목록 + 열기
- 메모 목록: 최근순 + 태그 필터 + 검색
- 메모 상세: 본문 + 붙은 일정 목록
- 설정: 구글 캘린더 연결, 알림 설정, 태그 관리

## 모호한 부분 (세션1에서 질문으로 나와야 함)

- "알림"은 브라우저 푸시? 이메일? 둘 다? — 아직 안 정함
- 첨부 파일 용량/확장자 제한 — 모름
- 태그 계층 구조 (부모/자식) 있는 게 좋은지 평면이면 충분한지 — 모름
- 메모 마크다운 렌더링 수준 (이미지 인라인? 코드 하이라이팅?) — 일단 텍스트 + 체크박스만 필수
- 일정 삭제 시 연결된 메모는? — 메모는 남기고 링크만 끊기는 게 기본값일 듯, 근데 확신은 없음
- 과거 일정/메모 보관 기간 — 고민 안 해봄

## 기술 선호 (확정 아님)

- 백엔드: Spring Boot + JPA (SDD 프로세스 문서가 Java 가정한 걸로 보임)
- DB: PostgreSQL
- 프론트: React + TypeScript
- 인증: 싱글 유저니까 일단 **간이 로그인**(ID/PW 하드코딩 수준도 OK). SSO나 OAuth는 안 씀.

## 파일럿으로서의 의도 (SDD 프로세스 검증용 메모)

이 요구사항은 SDD 프로세스를 한 사이클 돌려보는 데 목적이 있다. 그래서 의도적으로:

- **양방향 의존**(일정↔메모)을 포함 → session4/5 검증
- **공용 인터페이스 후보 2~3개**(NotificationSender, FileStore, TagProvider?) 자연 발생 → session5 검증
- **외부 연동 1개**(구글 캘린더) → session17 검증
- **모호한 부분 의도적으로 남김** → session1 인터뷰가 이걸 잡아내는지 검증

완성도보단 **프로세스가 어디서 막히는지 관찰**하는 게 진짜 목표.

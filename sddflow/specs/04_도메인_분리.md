# 도메인 분리

기준 입력: `02_도메인_분류.md` (8 도메인), `03_ERD.md` (8 테이블)

---

## 분리 원칙

1. **테이블 소유는 한 모듈에만** — 동일 테이블을 두 모듈이 쓰지 않는다.
2. **N:N 조인 테이블은 "행위 주체" 모듈이 소유** — 02의 행위 목록을 기준으로 결정.
   - `schedule_memo_link`: 02 "연결" 도메인에 "붙이기/해제" 행위가 있음 → 연결 모듈 소유
   - `schedule_tag`, `memo_tag`: 02 "태그" 도메인에 "일정·메모에 태그를 붙인다" 행위가 있음 → 태그 모듈 소유
3. **양방향 의존은 공통 인터페이스로 단방향화** — 03의 "schedule/memo 삭제 시 링크 정리"는 일정·메모 모듈이 직접 연결 모듈을 호출하지 않고, 공통 모듈의 도메인 이벤트(`ResourceDeletedEvent`)를 발행 → 연결·태그·첨부 모듈이 구독. 컴파일 타임 의존은 **하위(연결/태그/첨부) → 상위(일정/메모)** 단방향.
4. **공용 참조 테이블은 `user`** — 모든 리소스가 `owner_id` FK로 user를 읽는다. 쓰기는 사용자/인증 모듈만.

## 모듈: 일정

### 소유 테이블
- `schedule`: 일정 본체 (제목·시작/종료·장소·반복 규칙·알림 분, 03 §일정)

### 사용하는 공용 테이블
- `user`: 읽기 (owner_id로 소유자 검증)

### 의존하는 모듈
- 사용자/인증: 로그인된 사용자의 ID로 소유자 검사 (공통 인터페이스 `CurrentUser`로 주입)
- **삭제 이벤트 발행 측**: schedule 삭제 시 공통 모듈의 `ResourceDeletedEvent(SCHEDULE, id)` 발행 → 연결/태그/첨부/알림이 구독. 일정 모듈은 구독 측 모듈을 직접 모르지 않는다 (단방향 유지).

### 컨텍스트 크기 추정
- 테이블 수: 1개, 예상 명세 길이: 중 (CRUD + 반복 규칙 4종 + 캘린더 월/주 뷰 조회 + 알림 분 기본값)

### 컨텍스트 크기 추정

## 모듈: 연결 (일정-메모 링크)

### 소유 테이블
- `schedule_memo_link`: 일정-메모 N:N 연결 (origin: SCHEDULE_TO_MEMO/MEMO_TO_SCHEDULE, 03 §연결)

### 사용하는 공용 테이블
- `user`: 읽기 (양쪽 자산이 동일 소유자인지 검증)
- `schedule`: 읽기 (연결 대상 존재 검증, 캘린더 표시용 일정 정보 조회)
- `memo`: 읽기 (연결 대상 존재 검증, 메모 요약 조회)

### 의존하는 모듈
- 일정: schedule.id 존재 여부 확인 (공통 인터페이스 `ScheduleReader`)
- 메모: memo.id 존재 여부 확인 (공통 인터페이스 `MemoReader`)
- 사용자/인증: `CurrentUser` 주입
- **이벤트 구독 측**: `ResourceDeletedEvent(SCHEDULE|MEMO, id)` 구독 → 해당 ID가 포함된 link 행 일괄 삭제

### 컨텍스트 크기 추정
- 테이블 수: 1개, 예상 명세 길이: 소 (생성/조회/해제 3개 행위 + 양쪽 소유자 동일 검증)

### 컨텍스트 크기 추정

## 양방향 의존 해소 결과

02 의존 그래프에서 양방향이었던 쌍:

| 쌍 | 02의 양방향 표기 | 해소 방식 |
|----|----------------|----------|
| 일정 ↔ 연결 | 일정→연결("삭제 시 링크 해제"), 연결→일정("연결 대상") | 일정은 `ResourceDeletedEvent` **발행만**, 연결이 구독. 컴파일 의존: 연결 → 일정 (단방향) |
| 메모 ↔ 연결 | 동일 | 동일 패턴 |
| 일정 ↔ 태그 | 일정→태그("태그 부여"), 태그→일정(N:N 조인 소유) | "태그 부여" 행위를 태그 모듈에 귀속(02 행위 목록 근거) → 일정은 태그 모듈을 모름. 컴파일 의존: 태그 → 일정 (단방향) |
| 메모 ↔ 태그 | 동일 | 동일 패턴 |
| 일정 ↔ 첨부 | 일정→첨부("첨부 함께 삭제"), 첨부→일정("첨부 대상") | 일정은 이벤트 발행만, 첨부가 구독. 컴파일 의존: 첨부 → 일정 (단방향) |
| 메모 ↔ 첨부 | 동일 | 동일 패턴 |

- 모든 양방향 데이터 의존이 **공통 모듈의 인터페이스/이벤트**를 경유한 단방향으로 해소됨.
- 공통 모듈 추가 산출물(`/session5`에서 확정 예정):
  - 인터페이스: `CurrentUser`, `ScheduleReader`, `MemoReader`, `TagReader`, `LinkReader`
  - 도메인 이벤트: `ResourceDeletedEvent { type: SCHEDULE|MEMO, id, ownerId }`

## 최종 의존 그래프 (단방향)

```
사용자/인증 (루트)
   ▲
   │ CurrentUser
   │
   ├── 일정 ─────────┐
   │      ▲          │ ResourceDeletedEvent(SCHEDULE)
   │      │          ▼
   ├── 메모 ─────────┤
   │      ▲          │ ResourceDeletedEvent(MEMO)
   │      │          │
   │      │          ├── 연결   (ScheduleReader, MemoReader 사용)
   │      │          ├── 태그   (ScheduleReader, MemoReader 사용)
   │      │          ├── 첨부   (ScheduleReader, MemoReader 사용)
   │      │          └── 알림   (ScheduleReader, LinkReader, MemoReader 사용)
   │      │
   └── 검색 (ScheduleReader, MemoReader, TagReader 사용)
```

- 화살표는 **컴파일 타임 의존 방향** (호출하는 쪽 → 호출당하는 쪽).
- 일정·메모는 어떤 하위 모듈도 import하지 않는다 (이벤트는 공통 모듈로 발행).
